# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

C4 InsightOS — a business-operations platform ("if cash moves, content performs, or a lead
breathes — it gets tracked") for a high-ticket coaching / info-product business. It was seeded
from a single large Lovable prompt (preserved verbatim in `README.md`) but has since evolved
well past that spec. **`README.md` describes the original ask, not the current product** — for
what's actually shipped vs. planned, read `.lovable/plan.md` (a wave-by-wave gameplan) and the
module list in `src/lib/permissions.ts` / `src/components/app-sidebar.tsx`, which reflect real
state.

This app is built and iterated on primarily through [Lovable](https://lovable.dev); changes made
there sync straight into this repo. Several files carry a `// This file is automatically
generated. Do not edit it directly.` header (all of `src/integrations/supabase/*` except
`auth-middleware.ts`'s logic details) — treat those as generated integration glue, not
hand-maintained code.

## Commands

- `npm run dev` — start the Vite dev server (TanStack Start SSR).
- `npm run build` — production build (Cloudflare Workers target via `@cloudflare/vite-plugin`).
- `npm run build:dev` — build in development mode.
- `npm run preview` — preview a production build.
- `npm run lint` — ESLint (flat config, includes Prettier as a lint rule — `eslint.config.js`).
- `npm run format` — Prettier write across the repo.

There is no test suite/framework configured in this repo (no test script, no vitest/jest
dependency) — don't assume tests exist or try to invoke one.

Both `bun.lock` and `package-lock.json` are committed; `bunfig.toml` sets a 24h supply-chain
install guard (`minimumReleaseAge`). If you add a dependency published in the last 24h, you need
to add it to `minimumReleaseAgeExcludes` in `bunfig.toml` — confirm with the user before doing so.

## Architecture

**Stack**: TanStack Start (React 19, file-based router) + Supabase (Postgres/Auth) + Tailwind v4
+ shadcn/ui (new-york style), deployed to Cloudflare Workers.

### Routing

File-based routes live in `src/routes/`. `src/routeTree.gen.ts` is auto-generated by the
TanStack Router plugin — never edit it by hand, it regenerates on dev/build.

- `_authenticated.tsx` is the auth-gated layout (redirects to `/login` if no session, renders
  `AppSidebar` + `DateRangeProvider`). Every route named `_authenticated.<name>.tsx` nests under
  it and maps to `/<name>` (e.g. `_authenticated.dashboard.tsx` → `/dashboard`).
- Public routes outside the authed shell: `login.tsx`, `request-access.tsx`, `daily-win.tsx`
  (a no-login student check-in form), and `routes/api/public/*` (webhook/ingest endpoints,
  Typeform intake).
- `src/components/app-sidebar.tsx` is the canonical map of the product's modules/nav taxonomy —
  Overview, Sales Tracking (Leads, Messaging, Team, Hiring, Attribution, Traffic, and a Reps
  sub-group: DM Setter / Inbound Dialer / Closer), ContentOS, CopyOS (with a Generate sub-group),
  Fulfillment (Clients, Onboarding, Client Results, VSL Analytics), Ops (AI Insights, Event Bus),
  plus admin-only Access Control / Connectors. This mirrors the resource groups in
  `src/lib/permissions.ts`.

### Server functions: `.functions.ts` / `.server.ts` split

Business logic in `src/lib/` follows a strict two-file pattern per feature (e.g.
`daily-wins.functions.ts` + `daily-wins.server.ts`, `content-signals.*`, `copy-os.*`, `hiring.*`):

- **`*.functions.ts`** — the client-callable boundary. Defines `createServerFn(...)` RPCs with a
  Zod `inputValidator`, optionally gated by the `requireSupabaseAuth` middleware, and
  `await import("./x.server")`s the implementation inside the handler. This file is safe to
  import from routes/components.
- **`*.server.ts`** — the actual implementation: Supabase queries (usually via `supabaseAdmin`,
  the service-role client), AI calls, etc. Never import a `.server.ts` module from client code —
  only from its paired `.functions.ts`.

Follow this split when adding new server-side features rather than inlining logic into route
files or calling `supabaseAdmin` from a route component.

### Auth & multi-tenancy

- `src/integrations/supabase/client.ts` — browser Supabase client (anon key, RLS-scoped, session
  persisted to `localStorage`). Used directly in route components for reads.
- `src/integrations/supabase/client.server.ts` — service-role `supabaseAdmin` client that
  bypasses RLS. Only ever use it inside `.server.ts` files (trusted server context).
- `src/integrations/supabase/auth-middleware.ts` (`requireSupabaseAuth`) — server-side function
  middleware that validates the `Authorization: Bearer` token and injects
  `{ supabase, userId, claims }` into the server-fn context.
- `src/integrations/supabase/auth-attacher.ts` (`attachSupabaseAuth`) — client-side function
  middleware, registered globally as `functionMiddleware` in `src/start.ts`, that attaches the
  current session's access token to every `createServerFn` RPC call. Without this being
  registered, server fns never see the caller's identity.
- Every business table is scoped by `org_id` (a workspace). `useCurrentOrg()` /
  `ensureCurrentWorkspace` (`src/lib/workspace.functions.ts`) lazily provisions a
  workspace+membership for a new user and returns `{ org_id, role }`. `useRole()`
  (`src/hooks/use-role.tsx`) derives `isAdmin` / `canManage` / `canEdit` from that role.
- `src/lib/permissions.ts` is the access-control catalogue: it enumerates every sidebar
  "resource" with what View/Edit means for it, the six `ROLES`
  (admin/sales_manager/growth_ops/setter/closer/viewer), and `defaultPerm(role, resource)` — the
  fallback view/edit matrix used when no explicit per-user override row exists. When adding a new
  module/page, add a matching entry here so it's governable by the permissions system.

### Data layer

Postgres via Supabase; migrations in `supabase/migrations/` (chronological, RLS-first — new
tables should ship with `ENABLE ROW LEVEL SECURITY` + org-scoped policies, following existing
migrations). There's no ORM: route components query `supabase` directly for reads (RLS-scoped),
and `.server.ts` files use `supabaseAdmin` for writes/admin operations/AI calls.

### AI

Several `.server.ts` modules (daily-wins, content-signals, coach-content, copy-os, etc.) call the
Lovable AI Gateway directly (`https://ai.gateway.lovable.dev/v1/chat/completions`, bearer
`process.env.LOVABLE_API_KEY`, typically model `google/gemini-2.5-flash`) to generate
plain-language insight summaries from logged data. Follow the existing pattern (system prompt
with strict output sections, hard truncate the input log, graceful "AI is not configured" /
"AI error" fallback) when adding new insight generators rather than introducing a new SDK/client.

### Deployment / server entry

Targets Cloudflare Workers (`wrangler.jsonc`, `nodejs_compat`). `src/server.ts` is the actual
Worker entry (`wrangler.jsonc`'s `main`) — it wraps TanStack Start's generated server entry to
catch errors that h3 would otherwise swallow into a raw `{"unhandled":true,...}` JSON 500, and
renders a branded error page (`src/lib/error-page.ts`) instead. `src/start.ts` additionally
registers a server `errorMiddleware` and the client-side `attachSupabaseAuth` function
middleware — both need to stay registered for auth and error handling to work app-wide.

### UI conventions

- shadcn/ui components in `src/components/ui` (new-york style, Radix primitives, see
  `components.json`); Tailwind v4 configured via CSS (`src/styles.css`), no `tailwind.config.js`.
- `vite.config.ts` deliberately does not add `tanstackStart`/`viteReact`/`tailwindcss`/
  `tsConfigPaths`/`cloudflare` plugins itself — they're bundled inside
  `@lovable.dev/vite-tanstack-config`; adding them manually duplicates plugins and breaks the app.
- Dark mode is forced (`<html class="dark">` in `src/routes/__root.tsx`'s `RootShell`) — this is
  a dark-only, data-dense dashboard product, not a light/dark togglable one at the HTML level
  (there's still a `ThemeProvider`/`use-theme.tsx`, but the shell always renders dark).
- Path alias `@/*` → `src/*` (`tsconfig.json`).
- ESLint intentionally disables `@typescript-eslint/no-unused-vars` and `noUnusedLocals` — don't
  "fix" unused-var warnings project-wide, that's a deliberate config choice here.

### Env vars

Server: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`,
`SUPABASE_PROJECT_ID`, `LOVABLE_API_KEY`. Client bundle needs the `VITE_`-prefixed duplicates
(`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID`).
